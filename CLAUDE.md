## Commands

```sh
# Setup
python -m venv .venv && source .venv/bin/activate
make install-dev        # pip install -r requirements.txt -r requirements-dev.txt (one resolve, so both sets of constraints apply)

# Testing
make test               # static + unit + integration (non-slow); does NOT run docker tests
make test-static        # ruff check radiant/ scripts/upgrade_guide/
make test-unit          # unit tests only: pytest tests/unit/
make test-integration   # fast integration: pytest -m "not slow" tests/integration
make test-integration-slow  # pytest -m slow tests/integration
make test-docker        # build-docker, then pytest tests/docker/ (drives the compose stack)

# Run a single test file or test
pytest tests/unit/path/to/test_file.py
pytest tests/unit/path/to/test_file.py::test_function_name

# Linting & formatting
make test-static        # ruff check radiant/ scripts/upgrade_guide/ only
make format             # ruff format + ruff check --fix over radiant/ tests/ scripts/ecs/ scripts/upgrade_guide/

# Upgrade guide between two releases (needs the tags; TO may be main)
make upgrade-guide FROM=<vA> TO=<vB>
```

Integration tests select their fixtures via an env var (not a make flag):
```sh
USE_DOCKER_FIXTURES=true  make test-integration   # spins up local Docker (testcontainers): RustFS (S3) + Iceberg REST catalog. CI default.
USE_DOCKER_FIXTURES=false make test-integration   # runs against the external radiant-portal-sandbox environment
```
CI (`.github/workflows/test.yml`) runs on every PR with `USE_DOCKER_FIXTURES=true`: static → unit → integration → docker. Pushes to `main` and `v*` tags build/push the three images the deployments run: task operator, dbt, Nextflow launcher (`build_and_push_*.yml`). `main` pushes add `latest` and `<sha>-<timestamp>`, which QLIN QA follows with Flux image automation; releases deploy the `v*` tags. The root `Dockerfile` (`radiant-airflow`) is for the local docker compose only: MWAA (CHOP) and the QLIN Helm chart run the stock Airflow image, so it is neither published nor scanned. Security checks (radiant-hub `docs/ci/security-checks.md`): `dependency-review.yml` fails a PR that adds a high or critical vulnerable dependency, `trivy.yml` scans the three images and the Dockerfiles (PRs, main, daily on `latest`), `dependabot-alerts.yml` keeps a `dependabot-gate` issue and a Slack message up to date. Releases: `release.yml` runs release-please on each push to `main` (config `release-please-config.json`, type `simple`, last version in `.release-please-manifest.json`; token of the org GitHub App `radiant-release-please`, `RELEASE_PLEASE_APP_CLIENT_ID` variable + `RELEASE_PLEASE_APP_PRIVATE_KEY` secret, since `GITHUB_TOKEN` events start no workflow). It keeps one release PR, `chore(main): release <version>`, with the bump from the squash subjects since the last tag (`!`/`BREAKING CHANGE:` major, `feat` minor, `fix`/`perf`/`revert` patch, other types none); merging it commits `CHANGELOG.md` + manifest, tags `vX.Y.Z` and creates the GitHub release, and the tag builds the semver images. Do not tag by hand (README, "Release"). `release-gate.yml` runs only on the release PR (head branch prefix `release-please--branches--main`, skipped elsewhere) and blocks its merge while a high or critical Dependabot alert is open or Trivy finds a fixable high or critical vulnerability in one of the three images; a risk is accepted by dismissing the alert with a reason or by an entry in `.trivyignore.yaml` (README, "Release gate").

**Upgrade notes (RAD-186, README "Upgrade guide").** A PR whose deploy needs an operator action (a migration, a new env var, Airflow connection or variable, a DAG to run once, a re-import, a Nextflow pipeline revision, a breaking change) adds one YAML file in `upgrade-notes/`, named after the ticket (`RAD-171.yaml`, `RAD-171-2.yaml`): `actions:` list, each with `when` (`before`/`after` the deploy), `do`, optional `preconditions` and `refs` (the migration file or DAG, never a copy of its SQL), and `check`. Model, guide and PR-check rules in `scripts/upgrade_guide/` (outside the `radiant` package, not in the images; `python -m scripts.upgrade_guide guide|release-section|check`; unit tests in `tests/unit/upgrade_guide/`). A note's release is the first `vX.Y.Z` tag that contains the commit that added the file; the text always comes from `HEAD` (`main`), so a correction is a PR that edits the note — never delete one. The `upgrade-note` check (`upgrade-note.yml`, required) fails a PR that changes a migration with no note, a breaking PR (`!` in the title, or a `BREAKING CHANGE:` footer in the description) that adds no note, a deleted or malformed note, a file in `upgrade-notes/` that is not a note (subfolder, `.YAML`), a note in a PR whose type opens no release (not `feat`/`fix`/`perf`/`revert`, no `!`), and a note with an IP, a URL host off the allowlist (a bare host name is not detected), a 12-digit account number or a non-`<placeholder>` S3 bucket (`s3://` or S3 ARN; the notes are public). The job runs the checker of the base branch (`git archive $BASE`), so rule changes apply from the next PR. Use `!` for breaking changes: the squash message is the title only, so the footer never reaches release-please. The check's job summary previews the PR's notes as the guide will render them (`preview` subcommand). `release.yml` puts the guide from the last tag to `main` at the end of the open release PR description, after the release-please footer, between `<!-- upgrade-guide:start -->` / `<!-- upgrade-guide:end -->` (release-please reads its notes only between the first and last `---` lines, so the guide must hold no `---` line); the guide renders each step as a numbered subsection whose title is the first sentence of `do` (so write that sentence as a short order), with a "Change" list (one item per next sentence) and a "Refs" list whose paths of this repo link to the file at the release tag (in GitHub Actions only: `GITHUB_SERVER_URL`/`GITHUB_REPOSITORY`; DAG ids and other repos' files stay text); with one release (the release PR), the guide (title `#`) has no version heading, so its phases are `##` and its steps `###`; `upgrade-guide-release.yml` appends the "Upgrade guide" section to each GitHub release on `release: published` (or by hand, input `tag`, to fill or refresh it: a re-run of `release.yml` cannot, release-please does not create the release again); `upgrade-guide.yml` is the manual `workflow_dispatch` version (`from`, `to`) writing to the job summary.

**Integration test data.** `radiant/dags/sql/clinical/seeds.sql` feeds every clinical integration test, including the whole-delta row count in `tests/integration/dags/sql/test_sequencing_experiment_select_delta.py` (18 rows): a seeded document that the staging view admits moves that count, and so does the proband source rule (RAD-169: case 1's slivar VCF hides the proband's alignment task 1). Shapes the seeds do not have are inserted by test-local fixtures on ids far above the seeded range — 90xx–93xx are taken by `test_case_resolution.py`, 95xx by `test_somatic_case_resolution.py`, 96xx by `test_sequencing_experiment_select_delta.py`, 97xx by `test_qc_case_resolution.py`, 98xx by `test_pipeline_views.py`, 99xx by `test_gene_coverage.py` — and a fixture that inserts rows must delete them afterwards, or it changes the results of other tests in the same session. The same `seeds.sql` seeds the radiant-portal-sandbox clinical DB through the manual `init-qa-clinical-data.py` DAG (param `vcf_bucket_prefix`, `s3://vcf` in the sandbox): a seed change reaches the sandbox only when that DAG runs again, and it truncates every clinical table first. The files the seeds point to come from the sandbox repo's `data/` (synced to `s3://vcf/`).

### Local Airflow stack

`make build-docker`, then `docker compose up`. UI at `http://localhost:8080` (`airflow` / `airflow`). Create the MySQL connection `starrocks_conn` (Admin → Connections; e.g. host `host.docker.internal`, login `root`). In deployed environments, give it socket timeouts in `Extra` (`{"connect_timeout": 10, "read_timeout": 60, "write_timeout": 60}`): `StarRocksTaskCompleteTrigger` bounds each poll, but a timed-out poll's worker thread stays blocked in `recv()` on a half-open connection until a driver-level `read_timeout` releases it. Check the extras against the image's `apache-airflow-providers-mysql` version: the hook forwards only whitelisted extras, and an unknown key breaks `get_conn()`.

## Architecture

Apache Airflow ETL pipeline importing genomic data into a clinical data model. Two storage backends: **Iceberg** (data lake, via PyIceberg + Glue/REST catalog on S3) and **StarRocks** (OLAP analytics, queried over a MySQL-protocol connection `starrocks_conn`).

### Source layout

- `radiant/dags/` — Airflow DAG definitions (orchestration only). `radiant/dags/__init__.py` is the config module (see below). Each DAG's UI doc is `radiant/dags/docs/<dag>.md`, loaded via `load_docs_md(...)` into `doc_md` — update it with the DAG.
- `radiant/tasks/` — Reusable processing logic called by DAGs
  - `vcf/snv/germline/`, `vcf/snv/somatic/`, `vcf/cnv/germline/` — VCF variant extraction (cyvcf2)
  - `iceberg/` — table init, `table_accumulator.py`, partition commit
  - `starrocks/` — custom operators, partition assignment, deferrable trigger
  - `data/radiant_tables.py` — the table-name mapping resolved into SQL templates (see multi-tenancy)
  - `tracing/` — OpenTelemetry spans (exported per `otel-collector-config.yaml`)
- `radiant/dags/sql/{clinical,open_data,radiant}/` — Jinja SQL templates (each has an `init/` subdir for one-time DDL)
- `radiant/dags/operators/` — `k8s.py` and `ecs.py` task operators (selected at runtime, see deployment)
- `radiant/data_qa/` — standalone dbt project for data-quality assertions (see below); **not** part of pytest
- `tests/{unit,integration,docker}/`, `tests/resources/` — test suites + sample VCF/TSV data
- `mwaa/` — AWS MWAA + ECS deployment artifacts (dep builder in `airflow3/`)

### Data flow

```
VCF file → cyvcf2 parse
  → extract occurrences / variants / consequences (radiant/tasks/vcf/)
  → accumulate into Iceberg tables (radiant/tasks/iceberg/table_accumulator.py)
  → commit partition (radiant/tasks/iceberg/partition_commit.py)
  → load into StarRocks (radiant/tasks/starrocks/)
  → aggregate variant frequencies
```

### DAGs and the delta/incremental flow

- `import_radiant.py` — main scheduled import. Reads its facts (`sql/clinical/import_facts_select.sql`: the `importable_task` rows not in staging yet, with partition hints, plus the staged rows not loaded yet or of a deleted task), decides each (case, task) in Python (`radiant/tasks/importing/resolve.py`: run `first_run`/`retry`/`task_deleted`, or `blocked` when a new row lacks a required value, which blocks the task's new rows only) and journals it (`pipeline_journal`, pipeline `import`), moves the cases it loads (`first_run`/`retry`) to `processing` beside the load, assigns the new rows to partitions (`SequencingExperimentPartitionAssigner`), inserts them and flags the deleted tasks, then fires one `import_part` run per partition via `TriggerDagRunOperator`; `journal_import_outcomes` (`all_done`) journals `succeeded`/`failed` per item by reading the facts again and hands the cases that got new data to `radiant-case-evaluation` (not waited for). Only new (case, seq, task) keys are processed, never a row already in staging (RAD-377: no date, so a case status change re-imports nothing) — this is the incremental-loading mechanism (design: `design/SJRA-1187-*.md`).
- `import_part.py` — processes one partition: VCF extraction → Iceberg → StarRocks.
- **Two germline CNV sets per sequencing** (RAD-169/RAD-206, radiant-hub `docs/features/RAD-169-cnv-post-processing.md`): the DRAGEN set of each member's `alignment_germline_variant_calling` task, and the proband-only slivar set of the case's `radiant_germline_cnv_annotation` task (parental origin, transmission mode, `mother_*`/`father_*` columns, `name` from `FORMAT/OID`). Once a case has a slivar VCF, the staging view (`original_alignment` CTE) hides the proband's alignment task; a DRAGEN set already loaded stays. Because both sets share a `seq_id`, the copy step and every annotation join of `germline_cnv_occurrence_*.sql` are keyed on `task_id`, never on `seq_id` alone; the new columns are last because the insert is positional and the copy is `SELECT *`. Extraction: `radiant/tasks/vcf/cnv/germline/process.py` + `occurrence.py`. RAD-181: the CNV annotation task's Exomiser report (`exomiser_cnv`, proband row only) is loaded into its own `raw_exomiser_cnv` (`load_exomiser_cnv_files`), never `raw_exomiser`; `insert_exomiser_cnv` puts every row into the per-tenant `exomiser_cnv` (the twin of `exomiser`: `cnv_id` + `name` in place of `locus_id` + `locus_hash`, `variant_rank` per occurrence), matching `VCF_ID` on `name`, else on the Iceberg-only `vcf_id` (the record ID): Exomiser runs on the proband VCF (IDs = proband calls) or, without one, the family VCF (IDs = truvari-kept calls). The occurrence insert then copies the `variant_rank = 1` row onto the slivar set (six `exomiser_*` columns, last), as the SNV insert does from `exomiser`.
- **Gene coverage** (RAD-315, radiant-hub `docs/features/RAD-315-*.md`): Phase 3 of `import_part`, like Exomiser (`load_gene_coverage_files` after the Exomiser loads, `insert_gene_coverage` after `insert_exomiser`), loads the DRAGEN `coverage_by_gene` CSV (`covgene` document) of the current alignment (`current_alignment` view, both alignment task types) of each delta experiment. `RadiantLoadGeneCoverageOperator` reads each file's header on the worker (S3 ranged GET of the first 4 KiB, boto3; two formats: with or without a `type` column), broker-loads the files of one format together into the shared `raw_gene_coverage` (one job per `GENE_COVERAGE_FILES_PER_LOAD` files, one `data_desc` each; a job a bad file cancels is retried file by file), keeps going after a bad file and returns the errors; `insert_gene_coverage` applies the gene name rule per tenant (CDS rows only, `_chrX`/`_chrY` suffix, ENSG → `ensembl_gene.name`) into `gene_coverage`; `check_gene_coverage_files`, a leaf no task waits on, then fails the run naming each bad file. Both copy steps are keyed on `seq_id`, not `task_id`, so a re-alignment replaces the old coverage.
- `import_snv_vcf.py` — sub-DAG triggered by `import_part`, doing all SNV → Iceberg extraction. **Germline and somatic both live here on purpose**: each fans out one mapped writer per annotation task (pool `import_vcf`), and both fan into a *single* `merge_commits` → `commit_partitions`. `snv_variant` and `snv_consequence` are written by both flows, so one committer per part is what keeps their Iceberg commits from racing (design: `design/SJRA-1751-snv-vcf-ingestion-fan-out.md`).
- `nextflow_snv_postprocessing.py` / `nextflow_quality_control.py` — thin launchers: one Nextflow driver pod on k8s each. `nextflow_snv_postprocessing_cases.py` / `nextflow_cnv_postprocessing_cases.py` / `nextflow_quality_control_cases.py` — the automations around them (no schedule of their own, see `case_scheduler.py`): each starts with `radiant/dags/pipeline_decision.py` (facts `sql/clinical/<pipeline>_facts_select.sql` → `decide_run` → journal in `pipeline_journal` → the cases decided `run` to `processing`, except QC), runs what it decided (`case_ids`, `task_ids` for somatic SNV, only narrow it; each `succeeded` outcome names the task registered for the item, `output_task_id`, found back from one of its output URLs by `radiant/tasks/nextflow/lineage.py`, since the batch report carries no task id), build inputs on S3, trigger the launcher, register the outputs on the cases through the portal batch PATCH (`radiant/tasks/nextflow/`, QC-specific parts in `radiant/tasks/nextflow/qc/`). Designs: `design/SJRA-1698-*.md`, `design/SJRA-1879-*.md`. QC has one facts query and one members query per case type (`quality_control_{,somatic_}{facts,case_members}_select.sql`), journaled as two pipelines (`quality_control`, `quality_control_somatic`) that both name their cases to the one QC DAG. QC passes each sample's DRAGEN metrics in the samplesheet's `dragenMetrics` column (the alignment's `ssup`/`tgz` tarball, else the CRAM's directory) and runs every case in one launcher run (RAD-110, radiant-hub `docs/features/RAD-110-*.md`). Somatic cases run too, tumor alone (RAD-132): the tumor is a `VCF` row on an empty placeholder (`NEXTFLOW_QC_PLACEHOLDER_VCF`), so the pipeline skips somalier; its CRAM plays no role, it needs a tarball (no fallback, else `no_metrics`) that is the task's only input document; its outputs are collected like germline ones. Somatic SNV annotation (RAD-23) has its own pair: `nextflow_somatic_snv_annotation.py` (launcher: the SNV pipeline, image and `nextflow-snv-cfg` with `nextflow-snv-somatic-params`) and `nextflow_somatic_snv_annotation_cases.py` (unit of work: the calling task, per case, journal `item_key`; rules in `radiant/tasks/nextflow/somatic/`, query `sql/clinical/somatic_snv_facts_select.sql`, every candidate, or the named tasks only).
- **Nextflow concurrency.** All drivers share one FSx file system, and the launch dir, `workDir`, outputs and cleanup are all keyed by `RUN_TAG`. The case scheduler gives every cases DAG the same run id, so a cases DAG whose launcher could see the same tag must prefix it (the somatic one uses `somatic-`). The SNV, CNV and somatic launchers run one driver at a time (`max_active_runs=1`; the QC launcher allows 5): a germline WGS run leaves about 200–280 GB of scratch on the 1.2 TiB file system. Limit drivers per launcher DAG, not per task: the driver is deferred for almost all of its run, and Airflow counts deferred tasks neither for `max_active_tis_per_dag` (RUNNING and QUEUED only) nor for a pool without `include_deferred`.
- `case_scheduler.py` ("Radiant - Case Scheduler") — the single `@daily` entry point for case processing: triggers the four cases DAGs and, after germline SNV post-processing, somatic SNV annotation and germline CNV post-processing (the slivar VCF, RAD-206), the scheduled import, all `all_done`; `watcher` turns the run red on any failure. It decides nothing and moves no status (design: `design/RAD-288-pipelines-own-their-cases.md`): the pipeline DAGs and the import move their cases to `processing`. It passes `excluded_tenants` (default `$RADIANT_ETL_EXCLUDED_TENANTS`, from `radiant/dags/__init__.py`) to every DAG, and `notify` to the import. `case_evaluation.py` ("Radiant - Case Evaluation", started by the import with `case_ids`) moves to `in_progress` the named `processing` cases with imported variants none of whose germline SNV/CNV or somatic SNV items is `run` or `failed` in `pipeline_state` (`not_ready_cases`; QC does not count yet), and emails the labs of those and of the ready cases past `processing`: `evaluate_cases` mapped per tenant (`set_in_progress` → `create_case_group` `results-<run tag>` → `notify_labs`). Excluded tenants are left alone; a tenant without the grant is skipped on its 403. Rules in `radiant/tasks/nextflow/case_status.py`, query in `sql/clinical/case_status_select.sql`.
- `import_open_data.py`, `import_brim.py` — additional sources. `import_open_data` reads each open-data source either from the OpenDataLake catalog under its contract name or from the Radiant Iceberg catalog under its pre-contract name (`RADIANT_OPEN_DATA_USE_LEGACY_TABLES`), refreshes the StarRocks metadata cache first, and skips its cytoband broker load unless the caller passes its path. The `clinvar_rcv_summary` task group is one serial chain into the raw RCV table — an insert from the OpenDataLake `clinvar_rcv_v1` contract table (skipped when held back), then the broker load if `raw_rcv_filepaths` is passed, then the summary projection. `clinvar_rcv`, `ensembl_transcript` and `mane` are the contract sources with no pre-contract Radiant table: held back they resolve to no relation at all, leaving the broker load as the only way to fill the RCV table, and skipping `gene_reference_transcript`, the one insert built from two sources (rule in `gene_reference_transcript_insert.sql`). It also triggers `import_cosmic_gene_set.py` when given `cosmic_gene_set_filepath`: that DAG broker-loads the COSMIC Cancer Gene Census TSV into `cosmic_gene_set` (positional columns, transforms in the load's `SET` clause) and rebuilds `cosmic_gene_panel` from it — COSMIC has no OpenDataLake contract and is no longer an Iceberg source. Likewise `cosmic_mutation_set_filepath` triggers `import_cosmic_mutation_set.py`: a normalize task in the radiant-operator image (k8s or ECS; the image carries `bcftools`) rebuilds COSMIC's anchor-less indels as VCF records against the GRCh38 FASTA (`RADIANT_REFERENCE_FASTA_S3_URI`), left-aligns them, and writes a keyed TSV that is broker-loaded into `raw_cosmic_mutation_set` and deduplicated per locus into `cosmic_mutation_set` (`radiant/tasks/open_data/cosmic_mutation_set.py`); the rows coordinates cannot place (no GRCh38 position, strand-flipped liftover) are kept in the staging table with NULL keys and feed `cosmic_mutation_set_hgvs`, keyed on (Ensembl transcript without version, `c.` change). `snv_staging_variant_insert.sql` / `_reannotate.sql` denormalise both into the four `cmc_*` columns of the variant tables: the locus row when there is one, otherwise the HGVS row matching the picked `transcript_id` + `dna_change` (broadcast join), never a mix of the two. A COSMIC refresh is invisible to `reannotate_open_data`'s gate, so it needs a forced re-annotation.
- `reannotate_open_data.py` — weekly (Sat 00:00) open-data refresh: triggers `import_open_data`, then re-annotates what derives from it. Design: `design/SJRA-1811-opendatalake-integration.md`.
- **Import mutex**: `import_part` and `reannotate_open_data` share one S3 lock (`radiant/tasks/locking.py`, `_locks/import_mutex` in `RADIANT_LOCK_S3_BUCKET`, stale after 6 h) so they never write the same tables at once. `toolbox`'s `check-lock` command reports/clears it.
- `init_iceberg_tables.py`, `init_starrocks_tables.py`, `init-qa-clinical-data.py` — one-time setup.
- `diagnostics.py` — manual ops DAG (e.g. StarRocks DNS TTL checks).
- `toolbox.py` — manual: one maintenance command per run (`create-tenant`, `create-user`, `update-user`, `refresh-tenants` run the radiant-portal backend toolbox image on ECS/K8s; `check-lock` runs in-DAG).
- `data_integrity_starrocks.py` — runs the `data_qa` dbt suite in a container (ECS/K8s), reads results back from S3, optionally pushes JUnit to TestQuality (`testquality_conn`).
- `notify_cases.py` — manual re-send of a case group's lab email (`POST /{tenant}/case_groups/{name}/notify`); every run sends, no dedup.
- `import_igv_tracks.py` — manual, once per env: builds the public IGV reference tracks (+ tabix index) under one S3 prefix. Files only, no StarRocks/Iceberg.
- `import_tenant_gene_panel.py` — manual: reads one tenant gene panel `.tsv` from S3 and attaches it unchanged to one portal `PUT /{tenant}/gene_panels` (`radiant/tasks/gene_panel/upload.py`, client in `radiant/tasks/nextflow/portal.py`, connection `radiant_api_conn`). The portal parses the file (columns `symbol` + comma-separated `panels`) and sets the genes of all the tenant's panels from it (catalog panels keep their row, uploaded panels missing from the file are removed); the service account needs `can_manage_analysis_catalog`, not `ingest_data`. A 4xx fails with no retry, a 5xx is retried (the upload is idempotent). Design: radiant-hub `docs/features/RAD-10-*.md`.

### Partitioning

Partitioned by `experimental_strategy` so all experiments of the same patient/family/case/sequencing-id land together. First-partition masks: WGS `0x00000000` (100 experiments/partition), WXS `0x00010000` (1000). Assignment logic in `radiant/tasks/starrocks/partition.py`. Full strategy: `docs/RADIANT.md`.

### Deployment modes and config

`radiant/dags/__init__.py` centralizes config: `NAMESPACE`, `ICEBERG_NAMESPACE` (env-overridable), `DEFAULT_ARGS`, `load_docs_md`, `get_namespace`, and the `IS_AWS` flag. **`IS_AWS` (env var) is a load-time toggle**: `import_part.py` does `if IS_AWS: from radiant.dags.operators import ecs as operators else k8s`. On AWS, `ECSEnv` pulls `AWS_ECS_CLUSTER`/`_SUBNETS`/`_SECURITY_GROUPS` from Airflow Variables. `RADIANT_S3_WORKSPACE` (env var, every deployment) is the bucket where Airflow stores payloads too large to pass inline to a task (`s3_store_content`), e.g. the merged partitions `merge_commits` hands to the commit task. Three execution contexts:
- **KubernetesPodOperator** — K8s deployments (`IS_AWS=false`)
- **ECS task** — AWS ECS via custom operator (`IS_AWS=true`)
- **Local Docker Compose** — dev stack (`docker-compose.yml`): Airflow + PostgreSQL + Redis + RustFS (S3, keeps the `radiant-minio` host name) + Polaris

`Dockerfile` = Airflow image of the local docker compose only; `Dockerfile.radiant.operator` = task-execution image with all Radiant deps (K8s and ECS); `Dockerfile.radiant.dbt` = data QA runner; `Dockerfile.nextflow.launcher` = Nextflow driver.

### Multi-tenancy + SQL templating

Tables are **not** hard-coded in SQL. DAGs set `template_searchpath` to `radiant/dags/sql` and `render_template_as_native_obj=True`; the StarRocks operators inject a `mapping` dict and `tenant_code` into the Jinja context, so templates reference tables as `{{ mapping.some_table }}`. `radiant/tasks/data/radiant_tables.py` resolves that mapping from DAG-run conf + `tenant_code`: per-tenant tables route to a `{tenant}_tenant` database (`RADIANT_TENANT_DB_TEMPLATE`), shared/open-data tables stay in the base DB. `tenant_code` comes from the operator arg or `RADIANT_TENANT_CODE` in the DAG-run conf. Frequency math across tenants: `docs/frequency-calculation-multi-tenant.md`.

### StarRocks operator patterns

`radiant/tasks/starrocks/operator.py` — long-running loads run as StarRocks **async tasks** (`SUBMIT TASK`), then a **deferrable** `StarRocksTaskCompleteTrigger` (`trigger.py`) polls for completion without holding a worker slot. `SubmitTaskOptions` controls timeout/poll/spill. Key operators: `RadiantStarRocksOperator` (query + optional async submit + `output_processor`), `RadiantStarRocksPartitionSwapOperator` / `SwapPartition` (atomic partition replace for idempotent reloads), `RadiantLoadExomiserOperator`, `RadiantLoadGeneCoverageOperator` (broker loads, one job per batch of files — `EXOMISER_FILES_PER_LOAD` / `GENE_COVERAGE_FILES_PER_LOAD` — with one `data_desc` per file, each tagged in its `SET`; the load SQL is rendered twice, so per-file values are passed through as `{{placeholder}}` strings at the first render, and the `data_desc` loop sits in a `{% raw %}` block for the second render). Inserts serialize via `max_active_tis_per_dagrun=1` on the mapped operators plus the serial `>>` chains in `import_part.py` — note `STARROCKS_INSERT_POOL` is declared in `operator.py` but never referenced, so no pool is actually involved. Only one StarRocks INSERT may run at a time across all DAGs: add a new write to a serial chain, never as a parallel branch.

`import_part` phases (the `checkpoint_*` EmptyOperators; the flow is at the bottom of the file): 1 setup (lock, delta fetch) → 2 VCF imports (SNV sub-DAG + germline/somatic CNV pods, in parallel: no StarRocks write) → 3 post-VCF loads (Exomiser and gene coverage loads, Iceberg refresh, hashes, tmp variants, per-tenant Exomiser, gene coverage, comphet) → 4 SNV occurrences, variants, consequences → 5 CNV occurrences and frequencies → final sequencing-experiment delete/update, then the lock release (a teardown).

### Data QA (dbt) — separate from pytest

`radiant/data_qa/` is a dbt project (no models) asserting data quality against StarRocks. Run via `radiant/data_qa/scripts/run_qa.sh`: `run_qa.py` → `run_results_to_junit.py` → JUnit XML (test failures encoded in XML, exit non-zero only on connection/mechanism failure). Custom generic/singular tests live in `tests/*.sql`, reusable macros in `macros/`. **Two dbt sources, because tables live in two kinds of database**: `radiant` (shared, `SR_SCHEMA`) and `tenant_db` (per-tenant `{tenant}_tenant`, `SR_TENANT_SCHEMA`) — membership follows `STARROCKS_RADIANT_PER_TENANT_MAPPING` in `radiant/tasks/data/radiant_tables.py`. dbt resolves `source.schema` at parse time, so `run_qa.py` invokes dbt 1+N times (`--exclude source:tenant_db` once, then `--select source:tenant_db` per tenant) and merges the artifacts into the single `run_results.json`/`junit.xml` pair the DAG uploads; each result is stamped with its tenant. The tenant list arrives as the `TENANTS` env var (JSON, with schemas already resolved Airflow-side). The **"Values Contained In Dictionary"** tests exist to catch new upstream enum values the portal can't yet handle; their accepted-value lists (in `macros/dictionaries.sql`) mirror the portal's `backend/internal/repository/facets.go` **and** frontend i18n — keep them in sync when adding values. See `radiant/data_qa/README.md`.

## Linting conventions

Ruff (`.ruff.toml`): line length 119, Python 3.12, double quotes, Google-style docstrings. Rules: E, F, UP, B, SIM, I. `make test-static` only checks `radiant/` and `scripts/upgrade_guide/`; `make format` also fixes `tests/` and `scripts/ecs/`.
